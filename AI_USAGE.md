# AI_USAGE

> Все промпты и ответы нейронки, которые были использованы при разработке ДЗ. 

Использовалась Claude Haiku 5.5

## 1. Интерфейсы и обычный велосипед

**Промпт:** Смотри, у меня есть самокат, велик и электровелик. Я не очень понимаю, куда расход энергии деть. В общий интерфейс транспорта?

**Ответ нейронки:** Можно добавить `DailyEnergyKWh()` в `Vehicle`. Электротранспорт будет возвращать свой расход, а обычный велосипед — ноль.

**Промпт:** А зачем велосипеду вообще этот метод? И у меня ещё зарядный шкаф есть. Он энергию потребляет, но транспортом не является.

**Ответ нейронки:** Да, здесь лучше отдельный `EnergyConsumer`. Его будут реализовывать самокат, электровелосипед и зарядный шкаф. Обычному велосипеду и шлему он не нужен.

**Промпт:** А как потом сумму считать, если в списке разные объекты?

**Ответ нейронки:** Для каждого объекта проверять, реализует ли он `EnergyConsumer`:

```go
if consumer, ok := item.(domain.EnergyConsumer); ok {
    total += consumer.DailyEnergyKWh()
}
```

Это вариант для переменной `item` интерфейсного типа. В твоей обобщённой функции, где элемент имеет тип-параметр `T`, проверка записана через `any(item)`.

**Промпт:** То есть я не проверяю, самокат это или шкаф. Просто смотрю, есть ли у него нужный метод?

**Ответ нейронки:** Да. Поэтому при добавлении ещё одного потребителя энергии не понадобится дописывать отдельную ветку подсчёта для его типа.

## 2. Зачем нужен DI, если можно передать объект

**Промпт:** Объясни нормально, зачем мне контейнер. Я же могу создать сервис техосмотра и передать его в парк.

**Ответ нейронки:** Можешь. Передача зависимости в конструктор — уже dependency injection. Контейнер автоматизирует создание и связывание объектов. В этом задании он ещё и прямо требуется.

**Промпт:** Вот. А то звучит так, будто без библиотеки зависимости передавать нельзя.

**Ответ нейронки:** Библиотека для этого не обязательна. В твоём проекте парк принимает `Inspector`, а `dig` связывает этот интерфейс с `ServiceCenter` при сборке приложения.

**Промпт:** А сам парк про dig должен знать?

**Ответ нейронки:** Нет. `Fleet` достаточно обычного конструктора с аргументом `Inspector`. Вся настройка контейнера находится в пакете `di`.

**Промпт:** Окей. То есть парк можно и без контейнера в тесте создать?

**Ответ нейронки:** Да. Для тестов логики парка так и удобно делать. А отдельные тесты контейнера проверяют, что зависимости правильно связываются через DI.

## 3. ИИ предлагает тест, который не проверяет подмену через контейнер

**Промпт:** Подскажи тест, чтобы показать, что техосмотр можно подменить через DI.

**Ответ нейронки:** Создай заглушку `Inspector`, которая всегда отклоняет транспорт, и передай её в `fleet.New`. Потом проверь, что велосипед не добавился.

**Промпт:** Подожди. А где тут контейнер? Я его вообще не использую.

**Ответ нейронки:** Верно, такой тест проверяет только передачу зависимости через конструктор. Для проверки контейнера нужно создать его через `di.NewContainer`, заменить `Inspector`, а затем получить из него `Fleet`.

**Промпт:** А заменить как? Он там уже зарегистрирован.

**Ответ нейронки:** В твоей реализации тестов используется `Decorate`:

```go
err := c.Decorate(func(fleet.Inspector) fleet.Inspector {
    return fake
})
```

После проверки `err` получаешь парк через `Invoke`. Подмену нужно сделать до создания парка: уже созданный `Fleet` хранит ранее переданную зависимость.

**Промпт:** И что именно проверить? Просто что вернулся отказ?

**Ответ нейронки:** Возьми исправный велосипед, который настоящий сервис принял бы, а fake пусть отказывает. Проверь отказ, один вызов fake и пустой парк. Можно сделать обратный случай: fake принимает самокат с плохой батареей. Так видно, что решение приходит именно от подменённого инспектора.

## 4. Можно ли случайно обойти техосмотр

**Промпт:** А посмотри на RegisterItem. Он принимает Inventoried. Велосипед же тоже под этот интерфейс подходит?

**Ответ нейронки:** Да, потому что у него есть инвентарный номер и остальные необходимые методы.

**Промпт:** Ну тогда я могу его как вещь добавить. И он вообще техосмотр не пройдёт.

**Ответ нейронки:** Да, одной проверки интерфейса `Inventoried` недостаточно. В `RegisterItem` нужно отдельно отклонять объекты, реализующие `Vehicle`, чтобы транспорт добавлялся только через `AcceptVehicle`.

**Промпт:** Не через список типов? Типо если самокат или велик?

**Ответ нейронки:** Через интерфейс:

```go
if _, isVehicle := item.(domain.Vehicle); isVehicle {
    return ErrVehicleNeedsInspection
}
```

Тогда запрет сработает и для нового вида транспорта, который реализует `Vehicle`.

**Промпт:** Окей, а тест на это какой?

**Ответ нейронки:** Создать велосипед и передать его в `RegisterItem`. Проверить `ErrVehicleNeedsInspection`, что номер остался нулевым и что на балансе ничего не появилось.

## 5. Вариант упрощения, который нужно проверить

**Промпт:** Вот функция суммы энергии. Можно её как-то попроще сделать? Не нравится, что отдельно транспорт и вещи обходятся.

**Ответ нейронки:** Можно вызвать `Inventory()` и пройти по общему списку один раз. Так будет и короче, и быстрее.

**Промпт:** Почему быстрее? Inventory же ещё список создаёт и сортирует его. Для суммы зачем сортировка?

**Ответ нейронки:** Верно, про скорость я сказал без основания. В текущей реализации `Inventory()` делает дополнительную работу, которая для суммы не нужна. Два прохода по отдельным спискам всё равно обрабатывают каждый объект один раз.

**Промпт:** То есть лучше оставить как есть?

**Ответ нейронки:** Здесь да. Общая функция `dailyEnergyKWh` уже убирает повторение логики. Её можно вызвать для транспорта и вещей, а затем сложить результаты. Это также удобно для раздельных значений в сводке.

**Промпт:** Окей, лишь бы на защите можно было объяснить, зачем так сделано.

**Ответ нейронки:** Объяснение простое: ведомость сортируется для вывода, сумма считается без сортировки. У этих операций разные задачи.

## 6. Нормальный вывод в консоль

**Промпт:** Ещё хочу нормальный табличный вывод. Сейчас глазами искать номер и название неудобно.

**Ответ нейронки:** Можно сделать столбцы фиксированной ширины через `fmt.Printf`.

**Промпт:** А если название длинное? У меня и «велосипед», и «зарядный шкаф», и названия ещё разные.

**Ответ нейронки:** Тогда удобнее `text/tabwriter`: он выравнивает столбцы по содержимому. Для ведомости можно вывести номер, категорию, название и расход за сутки. Между столбцами — табуляция, в конце — `Flush()`.

**Промпт:** А у шлема в расходе что будет? Ноль?

**Ответ нейронки:** Можно поставить прочерк, потому что он не реализует `EnergyConsumer`. У потребителя с нулевым расходом вывести `0,00 кВт·ч`. Так эти случаи будут различаться.

**Промпт:** И чтобы порядок не менялся каждый запуск.

**Ответ нейронки:** Общую ведомость сортируй по номерам. Категории в сводке — по названию, потому что порядок обхода map не гарантирован. В твоём `report.go` уже используется сортировка ключей для этого вывода.
